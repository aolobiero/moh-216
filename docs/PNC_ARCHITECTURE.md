# Postnatal Care (PNC) Architecture

## Scope

PNC will be implemented as two related vertical slices:

1. Maternal postnatal visits linked to an existing `mother`.
2. Newborn follow-ups linked to an existing `child`.

No delivery entity is assumed yet. Delivery linkage can be added later with an
additive foreign key when the delivery module has been designed and verified.

## Proposed API

- `POST /api/pnc/mothers/{motherId}/visits`
- `GET /api/pnc/mothers/{motherId}/visits`
- `POST /api/pnc/children/{childId}/follow-ups`
- `GET /api/pnc/children/{childId}/follow-ups`

All endpoints remain behind the existing security filter until staff identity,
role, and facility authorization are implemented.

## Data model

`database/006_create_pnc_records.sql` defines:

- `pnc_visits`: recovery assessment, vital signs, breastfeeding support,
  maternal wellbeing notes, complications, family-planning counselling,
  referrals, and next visit date.
- `newborn_followups`: feeding notes, clinical notes, referrals, and next visit
  date linked to `children`.

The migration is additive and has not been executed.

## Backend design

- `PncVisit` and `NewbornFollowup` entities.
- Request/response DTOs with date and positive vital-sign validation.
- `PncService` for mother/child existence checks and persistence.
- `PncController` for the four endpoints.
- Service tests for missing references and successful synthetic records.

## Frontend design

- PNC navigation page with mother and child selectors.
- Separate maternal visit and newborn follow-up forms.
- History tables with loading, empty, validation, and error states.
- No clinical thresholds or treatment recommendations will be generated by
  the UI.

## Verification gate

Before marking PNC complete:

1. Obtain approval to execute migration 006.
2. Apply it against the development database.
3. Run authenticated API integration tests with synthetic records.
4. Verify existing mother, child, ANC, dashboard, and QR workflows remain
   functional.
